# 项目深度分析三文档（Project Deep Analysis）

对一个陌生的代码库做系统性分析，产出 3 份结构化学习文档，存放于该项目根目录下的 `学习文档/` 文件夹：

| 编号 | 文件名 | 内容 |
|------|--------|------|
| 01 | `01-STAR法则项目介绍.md` | 用 STAR 法则讲清楚项目是什么、为什么、怎么做 |
| 02 | `02-整体架构与模块详细设计.md` | 分层架构 + 逐模块职责/关键设计/依赖关系 |
| 03 | `03-MVP实现方案-模块取舍.md` | 若自己实现 MVP：选什么模块、放弃什么、为什么 |

## 工作流程

```
任务进度清单（复制到回复中跟踪）：
- [ ] 阶段1：侦察——摸清项目规模、技术栈、入口
- [ ] 阶段2：深读——逐模块理解关键实现
- [ ] 阶段3：写文档01（STAR 介绍）
- [ ] 阶段4：写文档02（架构与模块设计）
- [ ] 阶段5：与用户确认 MVP 目标形态/技术栈（仅首次）
- [ ] 阶段6：写文档03（MVP 取舍方案）
```

### 阶段1：侦察（先广度后深度）

1. 读 README、manifest（Cargo.toml / package.json / pyproject.toml）、
   目录树，确定：语言、规模（模块/文件数量、代码行数级别）、产品形态。
2. 找到入口点（main 函数 / CLI 命令 / 服务启动处），顺藤摸瓜走一遍
   主流程。
3. 若仓库带 `.qoder/repowiki`、ARCHITECTURE.md、CONTRIBUTING.md，优先读。
4. 产出侦察结论：一句话定位 + 规模数据 + 模块清单（供后续文档引用）。

### 阶段2：深读

- 按模块清单逐个看：每个模块至少确认「职责、对外接口、关键类型/函数、
  依赖谁、被谁依赖」。
- 大仓库优先用代码搜索/符号检索定位，不要全量逐文件读。
- 记录每个模块的代码量占比（文档中会用到）。
- 识别核心难点：项目真正解决的高价值工程问题（性能/并发/安全/协议等）。

### 阶段3-4：写文档01与02

按下文模板写作。两份文档共用阶段2的分析成果，01 偏叙事、02 偏工程细节。

### 阶段5：确认 MVP 前提（条件分支）

文档03 依赖两个前提，首次执行时用 AskUserQuestion 确认，后续同类项目
沿用用户已确立的偏好：

1. **目标形态**：如 CLI / Web 编辑器 / IDE 插件 / 本地服务
2. **技术栈**：如 Node.js/TypeScript、Python、Rust；是否允许复用开源基座

若用户已授权"直接采用推荐选项"或对话中已明确前提，跳过询问，
在文档开头声明前提即可。

### 阶段6：写文档03

按模板写作。核心要求：每个"选/弃"决策必须给出**原因**，
原因要落到具体成本（工作量、复杂度、与 MVP 目标的相关性）。

## 文档01模板：STAR 法则项目介绍

```markdown
# <项目名> 项目介绍（STAR 法则）

> 分析对象：<路径/仓库>
> 代码规模：<模块数、代码行数量级>
> 分析日期：<YYYY-MM-DD>

## S — Situation（背景与处境）
**行业背景**：该项目所在领域的演进趋势 + 3~5 条编号痛点（性能、
交互形态、安全、生态等维度，痛点要具体到场景）。
**主体的处境**：项目方为什么在这个时间点做这件事，手里有什么资源。

## T — Task（任务与目标）
一句话项目定位 + 目标表格：
| 目标 | 具体要求 |
|------|----------|
| <维度1> | <可验证的具体要求> |

## A — Action（行动与实现）
按架构分层（表现层/运行时/工具层/基础设施等）组织，每层列出：
- 模块名（代码量占比）：职责 + 1~3 条关键技术手段
重点写"怎么解决 S 中提出的痛点"，形成 S→A 的呼应。

## R — Result（结果与效果）
- 量化指标：性能数字、支持的能力清单、生态数据（有就写，无则标"待验证"）
- 与 S 中痛点逐条对照：解决了哪些、代价是什么
- 可借鉴点：3~5 条对其他项目有复用价值的设计决策
```

写作要点：
- S 的痛点必须在 A/R 中有呼应，形成闭环叙事。
- A 部分严禁罗列文件名，每个模块必须写清"它用什么手段解决什么问题"。
- 不确定的数字不编造，用"约"或注明推断依据。

## 文档02模板：整体架构与模块详细设计

```markdown
# <项目名> 整体架构与模块详细设计

> 分析对象：<workspace/仓库>（<模块数、代码规模>）
> 分析日期：<YYYY-MM-DD>

## 一、总体架构

### 1.1 分层视图
一张 mermaid `graph TB` 图：按层分组（subgraph），节点为模块，
边表示依赖/调用方向。层数 3~6 为宜。

### 1.2 数据流 / 生命周期
描述一次典型请求从入口到出口的完整路径（如：用户输入 → 解析 →
模型调用 → 工具执行 → 渲染），可用文字编号步骤或第二张 mermaid 图。

### 1.3 架构决策要点
3~6 条关键架构选择及其权衡（如：单进程 vs 多进程、同步 vs actor、
自研 vs 复用库）。

## 二、模块详细设计（逐模块）

### 2.x <模块名>（<代码量/占比>）
- **职责**：一句话说清边界
- **关键类型/组件**：核心 struct/class/函数及作用
- **关键设计**：值得学习的技术手段（算法、并发模型、协议、缓存策略等）
- **依赖与被依赖**：上游谁调它、下游它调谁

## 三、模块依赖关系总结
一张依赖汇总表或 mermaid 图 + 耦合度点评（哪些模块可独立抽出复用、
哪些是强耦合核心）。
```

写作要点：
- 模块粒度：以仓库自身的一级模块（crate/package/子目录）为单位，
  过小的工具模块可合并成"基础设施组"一节。
- "关键设计"是文档的灵魂，宁缺毋滥：只写真正有信息量的设计。
- 每个模块都要回答"如果没有它，系统会怎样"——答不上来就说明没读懂。

## 文档03模板：MVP 实现方案（模块取舍）

```markdown
# 如果我来实现一个 MVP：<目标形态 + 技术栈一句话>

> 前提：以 <原项目>（<规模>）为参照系，用 <技术栈> 实现 <形态> 的 MVP。
> 分析日期：<YYYY-MM-DD>

## 一、MVP 目标定义
**一句话**：<产品形态的最小完整定义>
**验收标准（DoD）**：编号列出 6~10 条可验证的具体标准。
**明确不做**：编号列出所有被砍掉的能力（与下文取舍表呼应）。

## 二、技术栈选型
| 关注点 | 选型 | 理由 |
|--------|------|------|
（每行理由必须具体，禁止"生态好""流行"这类空话；
优先复用成熟开源组件，注明哪些是"先薄实现、可升级"的项）

## 三、模块取舍总表
| 原项目模块 | 决策 | MVP 对应实现 | 理由 |
|-----------|------|-------------|------|
决策取值：**保留** / **简化** / **放弃** / **用开源替代**。
理由必须落到成本与价值：工作量多大、MVP 是否需要、替代方案是什么。

## 四、保留模块的简化设计
对每个"保留/简化"模块给出 MVP 版的最小设计：接口、存储格式、
关键流程，控制在能落地的颗粒度。

## 五、明确放弃的模块及原因
逐个说明：砍掉后用户体验损失多大、什么时候值得补回来。

## 六、实施路线图
| 阶段 | 交付物 | 预估工作量 |
（按依赖顺序排 3~5 个阶段，总工作量控制在 1~3 人周量级）
```

写作要点：
- 取舍的核心判据（按优先级）：① MVP DoD 是否必需 ② 自研成本
  ③ 有无成熟开源替代 ④ 是否是原项目的"差异化竞争力"（是则考虑简化保留）。
- "放弃"不等于"不重要"：要写清楚补回来的触发条件。
- 禁止照抄原项目架构——MVP 的价值正在于大刀阔斧地砍。

## 质量自检（三文档完成后逐条核对）

- [ ] 01 的 S 痛点与 A/R 形成闭环，无悬空痛点
- [ ] 02 的 mermaid 图能渲染，模块粒度与原仓库一致
- [ ] 02 每个模块都有"关键设计"，没有纯复述目录名
- [ ] 03 的每条取舍都有理由，理由含具体成本判断
- [ ] 03 的 DoD 与"明确不做"互不矛盾
- [ ] 三份文档互相引用一致（规模数字、模块名、日期）
- [ ] 无编造数据：不确定的标注"约/推断"
