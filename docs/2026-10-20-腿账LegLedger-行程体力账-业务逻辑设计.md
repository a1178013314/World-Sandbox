# 腿账 LegLedger · 行程体力账 · 业务逻辑设计

> ACC2026「AI+生活」赛道参赛方案 · 业务逻辑 v1.0（2026-10-20）
> 状态：定案待开发（48h 黑客松版本）。
> 上游判断：从「行程规划」红海中反向切出「体力可行性」——不帮你排行程，只告诉你**谁能走完**。
> 数据前提：不依赖任何私有数据，全部来自公开地图 API 与公开体力研究。

---

## 一、产品定义

**一句话**：把你的行程和同行人交给它，它给你一张按天结算的体力账单——哪天会崩、谁先崩、砍掉哪个点就能救回来。

- **Slogan**：行程不会累，腿会。
- **钩子记忆点**："这个 3 日游每天 18000 步、爬升 620 米——带 65 岁父母，第三天必崩。"
- **情感姿态**：不劝你别去，也不替你决定去哪；只把"走不走得动"这笔账算清楚，让尽孝不变成受罪。
- **赛道对位**：AI+生活 · 家庭出行子域。避开"行程规划/攻略生成/AI 导游"红海（那些解决"去哪、怎么玩"，我们解决"玩不玩得下来"）。

## 二、核心概念与口径（全产品的事实标准）

| 概念 | 定义 | 口径说明 |
|------|------|----------|
| 体力账 | 一天行程的体力消耗结算 | 字段：步数 / 步行距离 / 累计爬升 / 步行时长 / 在外时长 / 疲劳指数 |
| 疲劳指数 | 0–150+ 的可解释负荷分 | 由步数、爬升、在外时长加权，再乘年龄系数；**不是医学指标**，只用于横向比较 |
| 年龄系数 | 同行人的负荷放大倍数 | 65 岁以上 ×1.3，70 岁以上 ×1.5，6–12 岁 ×1.1，成年 ×1.0；体能偏弱再 ×1.1 |
| 红黄绿 | 当日负荷判定 | 绿 <60；黄 60–90；橙 90–120；红 >120（超出承受范围） |
| 崩溃日 | 首个红色日 | 演示主线必须让"崩溃日"出现在第 2 或第 3 天，符合真实旅行曲线 |
| 减负版 | 在不改变城市与天数的前提下重排 | 四类动作：砍点 / 换交通 / 坐缆车 / 调顺序；不新增景点、不延长行程 |
| **诚实原则** | **不声称"精确消耗卡路里"** | 统一口径："按公开步速与爬升折算的**估算负荷**，用于行程间横向比较，不构成医学建议" |

## 三、体力模型（核心算法，答辩重点）

### 3.1 输入

- 行程：城市 + 每天的景点序列（手工输入，或粘贴一篇攻略由 LLM 抽成结构化列表）；
- 同行人：年龄、体能标签（一般/偏弱）、负重（背包/婴儿车/行李）；
- 景点：类型（博物馆/观景台/商业街/山岳/古镇）、建议停留时长（可由类型默认）。

### 3.2 计算链路

```
景点名 → 地理编码（高德 POI）
      → 相邻景点步行路径（高德步行路径规划：距离 + 预计时长）
      → 路径采样点海拔（OpenTopoData / Open-Elevation，SRTM 30m）
      → 累计爬升 = 正向海拔差之和（过滤 <3m 噪声）
      → 全天步数 = (景点间路径距离 + 景区内步行估算) / 0.75
      → 等效距离 = 步行距离 + 爬升 × 8（Naismith 规则变体：100m 爬升 ≈ 800m 平路）
      → 基础负荷 = 100 × (0.3×步数/20000 + 0.4×爬升/750 + 0.3×在外时长/12)
      → 疲劳指数 = 基础负荷 × 年龄系数
```

> **步数口径（必须写死）**：全天步数 = 景点间路径距离 + 景区内步行估算，再除以 0.75m 步幅。路径 API 只算景点之间，景区里面走的这一段要单独估：山岳/古道 6km、观景台 1.5km、寺庙 1km、文创园 0.6km。步幅统一用成人 0.75m，老人差异只通过年龄系数体现，不在步幅上重复罚一次。
>
> 示例：Day 3 景点间 7.4km + 景区内 9.1km = 16.5km ≈ 22,000 步；等效平路 = 16.5 + 0.78 × 8 = 22.7km。
>
> 等效距离只用于页面文案（"相当于平路走了 22.7 公里"），不参与疲劳指数计算，避免同一因素被计两次。

### 3.3 判定与解释

| 指数区间 | 判定 | 文案 |
| --- | --- | --- |
| < 60 | 🟢 轻松 | "这天可以再加一个点。" |
| 60–90 | 🟡 偏紧 | "能走完，但中间必须坐一次。" |
| 90–120 | 🟠 吃力 | "老人会开始找椅子，孩子会开始要抱。" |
| > 120 | 🔴 崩溃 | "这天走不完。不是意志问题，是膝盖问题。" |

**复算示例（65 岁系数 1.3，演示锚点）**：

| 天 | 步数 | 爬升 | 在外 | 基础负荷 | 疲劳指数 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| Day1 解放碑—洪崖洞 | 10000 | 100m | 8h | 40 | 52 | 🟢 |
| Day2 磁器口—李子坝 | 15000 | 350m | 10.5h | 68 | 88 | 🟡 |
| Day3 南山—鹅岭 | 22000 | 780m | 12.5h | 106 | 138 | 🔴 |
| Day3 减负版 | 15000 | 250m | 11h | 63 | 82 | 🟡 |

**为什么不用 LLM 估**：LLM 给不出"4.7 公里、爬升 620 米、老人步速 3.6km/h"这种数字。这些数字来自路径 API 与海拔数据，模型只负责把数字翻译成人话。

### 3.4 减负规则（首版 8 条）

1. 单段步行 > 2km → 建议打车或公交；
2. 单日爬升 > 300m → 建议缆车/索道；
3. 连续两天橙色以上 → 建议第三天改为"半日行程 + 下午休息"；
4. 同一天跨两个以上景区 → 建议砍掉停留最短的那个；
5. 山岳类景点排在第一天 → 建议后移（体力最好的一天留给最难的点）；
6. 博物馆 > 2 小时 → 建议拆成两段，中间安排坐下休息；
7. 正午 12:00–14:00 安排户外爬升 → 建议与室内点对调；
8. 红色日无法避免 → 明确写出"这天需要有人留在酒店陪老人"。

## 四、用户旅程

**首次（< 2 分钟，演示主线）**：
1. 选城市模板（重庆/杭州/西安），或粘贴一篇攻略；
2. 填同行人：父亲 68 岁、母亲 65 岁、孩子 7 岁、自己；
3. 管线跑：地理编码 → 步行路径 → 海拔采样 → 体力结算；
4. 三天路径在地图上依次染色（绿→黄→红）；
5. **崩溃日弹出**：第 3 天 22000 步、爬升 780 米，疲劳指数 138——"是轻松上限的 2.3 倍"；
6. 一键出减负版：砍 1 个点、2 段改打车、1 段坐缆车 → 第 3 天回到黄色；
7. 分享：一张"体力账单卡"发家庭群。

**赛后留存（路线图，48h 不做）**：
- 行程执行后回填真实步数（手机健康数据），校准体力模型；
- 家庭体力档案：同一个人的年龄系数随年份更新；
- 景区"体力标签"：把每次计算的爬升数据沉淀成景点库。

## 六、演示脚本（3 分钟）

1. **0:00–0:30 痛点开场**：黑屏一行字——"你带爸妈去重庆，第 3 天他们说'不走了'。不是不想，是走不动。"（现场安静两秒）
2. **0:30–1:20 现场输入**：选重庆模板，填"父亲 68、母亲 65、孩子 7 岁"，点"算账"；
3. **1:20–2:10 魔法时刻**：地图上三天路径依次亮起——Day1 绿、Day2 黄、Day3 红。镜头推近：**22000 步 / 爬升 780 米 / 疲劳指数 138 / 超出 65 岁承受 2.3 倍**；
4. **2:10–2:40 减负版**：一键重排——砍掉鹅岭二厂、李子坝改打车、南山改坐缆车 → 第 3 天回到 82（黄色），文案"能走完，但中间要坐一次"；
5. **2:40–3:00 收尾**："行程可以重排，父母的膝盖不能。"

## 八、数据与合规

- **数据来源**：高德/百度地图步行路径 API（公开申请）、OpenTopoData/Open-Elevation 海拔（公开）、Naismith 步行规则与公开步速研究（文献）；
- **不采集**：真实定位、健康数据、身份证信息；同行人只填年龄与体能标签；
- **本地处理**：行程与计算结果存 localStorage，可一键清空；
- **口径边界**：明确写"估算负荷，不构成医学建议；有基础疾病请遵医嘱"；
- **演示样本**：3 个城市模板为公开景点，同行人参数为虚构。

### 8.1 外部数据接入契约

三类数据，三个来源，不能混用：

| 数据 | 接口 | 用途 | 备注 |
| --- | --- | --- | --- |
| 景点坐标 | 高德 `/v3/place/text` 或飞猪 `search-poi` | 景点名 → 经纬度 | 高德准到门牌，飞猪覆盖更全 |
| 步行路径 | 高德 `/v3/direction/walking` | 景点间距离、时长、路径点 | 飞猪没有步行路径，只能靠高德 |
| 海拔 | OpenTopoData `srtm30m` | 累计爬升 | 公开免费，无需 key，限 1 次/秒 |

**MCP 还是 REST**：高德 MCP 与 REST 拿到的是同一套数据。MCP 适合 agent 边聊边查，REST 适合批量抓一次存下来。演示读本地 JSON，不怕限流和断网。

**执行方式**（key 到位后）：

```bash
cd legledger-demo
AMAP_KEY=你的key node scripts/fetch-trip.mjs
```

产出 `data/day3.json`，页面上的数字以它为准。`data/day3.sample.json` 是格式参照，字段与脚本输出完全一致。

**验收标准**：跑出来的疲劳指数如果和 138 差很多，就改页面数字，不改公式。这是方案能不能站住的分界线。

**key 管理**：只用环境变量传入，不写进代码、不提交仓库。

## 九、竞争与差异

| 竞争位 | 它们做什么 | 我们不做什么 | 差异 |
| --- | --- | --- | --- |
| 行程规划器（飞猪/马蜂窝/小红书攻略） | 帮你排"去哪、几天、怎么走" | 不排行程、不推荐景点 | 我们只算"排好的行程走不走得动" |
| 地图 App 步行导航 | 告诉你怎么走、多远 | 不做多日行程、不合成体力账 | 我们把 3 天 × 5 个点合成一张体力账 |
| 运动 App / 健康数据 | 记录你走了多少 | 不做事前预测 | 我们是**事前**算账，不是事后记录 |
| AI 导游 / 讲解 | 让你看懂 | 不碰内容 | 我们只碰腿 |

**一句话差异**：别人优化"体验"，我们优化"可行性"。

## 十、护城河：为什么通用智能体做不了

- 问 LLM"这个行程累不累"，它只能给"比较累，注意休息"；
- 要给出"18000 步 / 爬升 620 米 / 疲劳指数 138"，必须调用**路径规划 + 海拔采样**，并跑**确定性体力模型**；
- 换一个同行人（65 岁 vs 30 岁），结论会翻转——这是**参数化计算**，不是语言生成；
- 输出可复算：同一个行程、同一组参数，任何人重跑都得到同一个数字。LLM 做不到"可复算"。

## 十一、风险与应对

| 风险 | 应对 |
| --- | --- |
| 地图 API 配额/限流 | Day 1 跑完即本地缓存；演示读缓存，不读实时 API |
| 海拔数据稀疏/失真 | 重庆用高德地形或人工校准 3 个关键爬升段；输出标注"估算" |
| 景区内部道路无法步行规划 | 按直线距离 × 1.3 估算，并在页面标注"景区内部估算" |
| 体力模型被质疑"拍脑袋" | 公式公开、参数可调、引用 Naismith 规则与公开步速；输出区间而非点值 |
| 被当成医疗建议 | 口径写死"不构成医学建议"；不做心率/血压/卡路里 |
| 演示时第 3 天不够红 | Day 1 就把"重庆 3 日带 65 岁父母"这条样本调到 130+，作为演示锚点 |
| 评委说"这不就是行程规划" | 第一句话就切："我们不排行程，我们算这笔行程谁的腿先垮。" |

## 十二、自评（48h 版）

贴题 9/10｜魔法时刻 9/10｜真功夫 8/10｜分享 8/10｜可行性 9/10 → **约 87，稳奖档**。

**最强的一点**：钩子具体到数字，评委一听就懂，且无法反驳——因为数字是算出来的，不是编的。
**最弱的一点**：分享场景偏家庭群，不如"发朋友圈"泛；靠"体力账单卡"补传播。

## 十三、与知识库范式的对位（内部溯源，对外不提）

- **Tailored Labs**：关键帧时间轴 → 换成"体力轴"（每天一个负荷刻度）；
- **Psych-MAP**：跨源异构对齐 → 行程、路径、海拔、人员参数四源对齐到同一天；
- **ModelProof**：置信度门禁 → 疲劳指数超阈值触发"崩溃日"判定与减负建议；
- **Paccelerate**：从图像估算物理量 → 换成从路径与海拔精确计算体力负荷（同属"把感觉变成数字"）；
- **反面对照**：行程规划 / 攻略生成 / AI 导游（红海），我们站在"可行性审计"位。
